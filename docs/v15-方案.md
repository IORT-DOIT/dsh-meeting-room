# v15 方案：文件夹改用系统界面选择 / 与会者消息堆积去重 / 页头按钮去重

> 用户原文（User said, m03783，**摘意**，逐字原文见会话记录）：
> ① **文件夹组件只保留 2 个功能：显示文件夹、选择文件夹。** 其中「选择文件夹」应直接打开**系统文件夹界面**，用户可以在系统界面里选择文件夹或新建文件夹。为避免用户找不到有用的文件，**附件与记录需分别用两个文件夹存放（在用户选择的文件夹下）**。
> ② **会议进行一段时间后，与会者的界面里会堆积很多待发送的信息**（截图一：同一个会话挂着「3 条排队消息」），查明原因，看能不能优化改正。

> 约束（User said, m00280 也要求过，m03783 重申）：「**仍遵循最小改动原则，检查 bug 与稳定性**」。

本文只记录 v15（包版本 `0.15.0`）改了什么、为什么这么改、验证到什么程度。契约仍以 `docs/v8-API.md` 为唯一来源（顶部已加 v9–v15 告示），v9–v14 见各自 `docs/v9-方案.md`…`docs/v14-方案.md`。

## §0 取证：DSH 里怎么弹出「系统文件夹界面」

### 0.1 宿主插件**拿不到** Electron 对话框

宿主进程是 `ELECTRON_RUN_AS_NODE=1` 的纯 Node（`lib/main.js:3529-3538`、`:3671-3691`），91 个宿主 Service 里没有 electron / dialog / BrowserWindow。所以插件不能在宿主侧直接 `dialog.showOpenDialog`。子代理 C 的报告（`%TEMP%\mr-picker-report.md`）与我的实读一致。

### 0.2 真正的桥在 preload（渲染进程全局）

- `lib/preload-app.cjs:861`：当 `location.protocol === 'dsh-app:' && location.hostname === 'app'` 时 `exposeInMainWorld('__DSH_DIRECTORY_PICKER__', { pick: () => ipcRenderer.invoke(DESKTOP_IPC.directoryPick) })`（取消返回 `null`）。
- 主进程侧：`installDesktopDirectoryPicker()` → `ipcMain.handle('dsh-desktop:directory-pick')` → `dialog.showOpenDialog(window, { properties: ['openDirectory', 'createDirectory'] })`（`lib/main.js:6240-6257`，安装点 `:11552`，按窗口去重 `:6246-6247`）。`createDirectory` 就是「在系统界面里新建文件夹」这个能力。
- 同一份 preload 还暴露 `__DSH_HOST_PATHS__ = { pathFor: (file) => webUtils.getPathForFile(file) }`（`:862`）。

### 0.3 第一方还有两条同类通路（作兜底）

- 客户端服务 `uiWorkspace.pickDirectory(): Promise<string | null>`（`dsh-client-ui-workspace/lib/client.js:100-104`，inject `'remote.directoryPicker'` `:2717`）——跨桌面/浏览器都可用。
- 宿主侧服务族 `ctx.directoryPicker`（Windows 走 COM `IFileOpenDialog`，独立子进程 + IPC：`dsh-host-directory-picker-native/lib/index.js:21-22`、`:86-90`；`dsh-host-directory-picker-auto/lib/index.js:64-70` 在本机 127.0.0.1 + win32 + 非 SSH 时挂 native）。

### 0.4 为什么**不用** `window.showDirectoryPicker()`

`dsh-app` 窗口是 secure + standard context（`lib/main.js:11019-11029`），权限处理器对非 `media` 权限一律放行（`:6274-6296`），静态看没被禁；但它只给 `FileSystemDirectoryHandle`，**换不出绝对路径**（`webkitdirectory` + `pathFor` 那条路空目录会失效）。对「把房间目录设成这个绝对路径」这个需求无用。

### 0.5 「在资源管理器中打开」同理

`showItemInFolder` / `shell.openPath` 没暴露给插件（全库 0 命中），但第一方有 `POST /open-in-app/open { app, path }`（`dsh-host-open-in-app/lib/index.js:118-125` / `:1186`；path 必须绝对且已存在 `:1423-1440`；过 Host/Origin + 登录 cookie 围栏 `:1195-1202`），`app: 'explorer'` 即资源管理器。

⇒ **v15① 的客户端形状被这两条事实定死**：优先用 preload 桥，退 `uiWorkspace`，再退房间内浏览式 `DirPicker`；「打开文件夹」优先 `/open-in-app/open`，退「复制路径」。

## §1 v15①：文件夹组件 = 显示文件夹 + 选择文件夹（系统界面）

### 1.1 客户端新增两个帮助函数（`client/client.js:543-589`）

```js
async function pickSystemFolder() {        // client/client.js:550-569
  const bridge = globalThis.__DSH_DIRECTORY_PICKER__;
  if (bridge && typeof bridge.pick === 'function') {
    try {
      const picked = await bridge.pick();
      if (typeof picked === 'string' && picked) return picked;
      if (picked === null || picked === '') return null;
    } catch { /* 落到 ② */ }
  }
  let workspace = null;
  try { workspace = (hostCtx && hostCtx.get && hostCtx.get('uiWorkspace')) || null; } catch { workspace = null; }
  if (workspace && typeof workspace.pickDirectory === 'function') {
    try {
      const picked = await workspace.pickDirectory();
      if (typeof picked === 'string' && picked) return picked;
      if (picked === null || picked === '') return null;
    } catch { /* 落到浏览式 */ }
  }
  return undefined;
}
```

返回三态，调用方据此分流：**字符串 = 选中目录**；**`null` = 用户取消**；**`undefined` = 两条系统通路都没有 ⇒ 退回房间内浏览式**。

```js
async function revealDirInOS(dir) {         // client/client.js:577-589
  const target = apiDirPath(dir);
  if (!target) { toast('该会议室还没有目录', 'error'); return; }
  try {
    const res = await fetch('/open-in-app/open', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ app: 'explorer', path: target }),
    });
    if (res.ok) return;
  } catch { /* 退回复制路径 */ }
  await revealDir(target);                 // 老行为：复制路径到剪贴板 + toast
}
```

注意这里**必须用裸 `fetch`**：客户端的 `json()` 帮助函数会自动拼 `${API}${path}`（`API = '/dsh-room'`），而 `/open-in-app/open` 是宿主第一方端点，不在 `/dsh-room` 前缀下。

### 1.2 `DrawerFiles` 的「文件夹」段（`client/client.js:2078-2123`）

删掉的三件套：`const [newName, setNewName]`、「换个文件夹」输入框 + 「新建」按钮、「选一个已有文件夹」开关，以及 `pickLabel: '把整个会议室放到这个文件夹里'`。新形态只有一行两键：

```js
h('div', { style: S.boxHead }, '文件夹'),
h('div', { style: S.note, title: dir }, dir || '（未知）'),        // 显示文件夹
h('div', { style: S.row },
  h('button', { type: 'button', style: S.btnTiny, onClick: () => revealDirInOS(dir) }, '打开文件夹'),
  h('button', { type: 'button', style: S.btnTiny, onClick: () => { chooseFolder(); } }, '选择文件夹')),
```

```js
const chooseFolder = async () => {          // client/client.js:2086-2091
  const picked = await pickSystemFolder();
  if (picked === undefined) { setPick(true); return; } // 没有系统文件夹界面 ⇒ 退回房间内浏览式
  if (!picked) return; // 用户在系统界面里取消了
  await act(() => patchJson(`/rooms/${q(roomId)}`, { dir: picked }), '已换好文件夹');
};
```

**选中的文件夹就是房间目录本身**——客户端不再拼 `<文件夹>\<房间id>`。宿主那侧本来就如此：`PATCH /rooms/:id {dir}` 里 `const nextCategory = rawDir ? dirname(resolve(rawDir)) : resolve(rawCat); const candidate = rawDir ? resolve(rawDir) : join(nextCategory, room.id);`（`index.js:2529-2563`）。所以 v13 那个客户端助手 `joinPath(base, name)`（唯一用途就是拼房间 id）**已删除**（`client/client.js:526-527` 只留一行说明）。

『附件』『记录』两个子文件夹仍是宿主的固定布局：`const RECORDS_DIRNAME = '记录'` / `'附件'` / `'结果'`（`index.js:41-43`），`this.recordsDir = join(dir, RECORDS_DIRNAME)` / `this.resultsDir = join(this.recordsDir, RESULTS_DIRNAME)` / `this.attachmentsDir = join(dir, ATTACHMENTS_DIRNAME)`（`index.js:433-435`）——与会者写进「附件/」，记录员与《会议结果》在「记录/」。

页尾提示同步改成：「选中的文件夹就是这个会议室的文件夹：「记录/」放记录员的记录与《会议结果》，「附件/」放其它会议文件（含与会者写的材料）。换文件夹会把整个会议室一起搬过去。」

### 1.3 宿主护栏：不许住进「别人的会议室文件夹」

v13 的三道换目录护栏（自己的子目录 / 分类目录本身 / 同路径）保留；v15① 在 `moveTargetReason` 末尾**加一道**（`index.js:1368-1373`）：

```js
const meta = await readJsonFile(join(target, 'room.json'), null).catch(() => null);
if (meta && typeof meta === 'object' && meta.id && meta.id !== room.id) {
  return `这个文件夹已经属于另一个会议室（${meta.id}）：${target}。两个会议室的「附件/」「记录/」会混在一起，请换一个文件夹，或在系统文件夹界面里新建一个子文件夹。`;
}
```

系统文件夹界面能**新建文件夹**，所以「目标被占用」不再是死胡同——用户可以在系统界面里新建一个子文件夹再选它。

## §2 v15②：与会者界面里堆积的「排队消息」

### 2.1 根因（子代理 D 报告 `%TEMP%\mr-inbox-report.md` + 实机日志）

- 插件每次有人 `room_say` 都会给**其他每位与会者各投一条提示**（自动接力：`index.js:3302-3321` → `deliver({ mode: 'notice', noticeStyle: 'ping' })`）。
- DSH 的 `agent.followup` 把消息放进 inbox 的 **next-turn** 列表，而 **每轮只领取 1 条**（`dsh-agent-loop/lib/index.js:103-111`：next-step 整批取走、next-turn 只取 1）。成员忙的时候只能不断 append ⇒ N 条提示 = N 行「排队消息」+ N 个额外轮次。
- 实机取证（成员会话 `session-273224f6-…`）：60 条提示进箱、59 条被领取；next-turn 峰值深度 6，深度分布 `{0:94, 1:104, 2:18, 3:12, 4:7, 5:4, 6:1}`，`removedCount` 恒 0（**全树没有任何 coalesce/dedup**）。截图一的「3 条排队消息」正对应连续的三条提示。

### 2.2 为什么不改 DSH

宿主侧公开 API 里 `Inbox` 已有 `locate/append/prepend/replace/remove/splice/clear`（`dsh-api-session-controller/lib/typert.host.js:1581`、`:1817`；`dsh-agent-loop/lib/index.js:163-172` 的 `locate(messageId) → { target, index }`），GUI 的「排队消息」读的就是同一份 `inbox.getSnapshot()['next-turn']`（`dsh-client-ui-conversation/lib/client.js:14148`）。⇒ **插件侧就能做去重，不必动 DSH 本体**（符合「不改插件以外任何东西」的约束）。

### 2.3 实现：同一位与会者**最多挂一条未领取的提示**

`relayWithEffort`（`index.js:1666-1692`）：`options.coalesceKey` 非空时，先看这个 key 有没有「还没被领走」的槽位；有就**原地换掉**那条提示，没有再走原来的 followup：

```js
const key = options.coalesceKey ?? null;
const slot = key ? this.pendingPings?.get(key) : null;
if (slot && this.replacePendingPing(key, room, agent, slot, text, level)) {
  return Promise.resolve({ ok: true, rpcId: slot.rpcId, coalesced: true });
}
```

`replacePendingPing`（`index.js:1700-1724`）：`inbox.locate(slot.messageId)` 命中才换，`locate` 失败/已被领走/宿主没给 `inbox` 一律 `return false`（并删槽），调用方随即**退化为普通 followup**——也就是「**宁可不合并，也绝不丢提醒**」。替换前按同一个 `rpcId` 重挂 `staging.expect` 与 `effort.prepare`（插入事件已经把这两处的 pending 认领掉了）；新消息用 `createUserMessage({ content: [{ type:'text', text }], source: { ...slot.source } })` 生成——DSH 的 `id` 由工厂生成且消息体 deepFreeze（`dsh-llm/lib/types/message.js:34-39`），所以只能「用新 id 的新消息换掉旧 id 的那条」。

`rememberPendingPing`（`index.js:1727-1736`）把刚投出去的那条记进 `this.pendingPings`（懒建的 `Map`，key = `${room.id}|${member.sessionId}`，不碰构造函数）。

只对**自动接力的 ping** 生效（`deliver` 的调用点，`index.js:841-846`）：

```js
const outcome = await this.host.relayWithEffort(this, member, `${finalText}${fileHint}`, {
  senderSessionId,
  coalesceKey: noticeStyle === 'ping' && mode === 'notice' ? `${this.room.id}|${member.sessionId}` : null,
});
```

⇒ 人类发帖、`mode='full'` 的正文、目标类投递**完全照旧**（每次都是新一条），只有「有新发言，来看一眼」这种可替换的提醒会被合并；合并后那一行提示里的序号/文案会刷新到最新，成员界面最多 1 行，且不会少跑轮次（该领还是要领）。

## §5 诚实边界

1. **`__DSH_DIRECTORY_PICKER__` 在 `http://127.0.0.1:19387` 页面上是否存在，只能实机确认**：preload 注入条件写的是 `location.protocol === 'dsh-app:' && location.hostname === 'app'`（`lib/preload-app.cjs:861`），而用户用的是 http 页面。若为 `undefined`，`pickSystemFolder()` 会走 `uiWorkspace.pickDirectory()`；若两条都不可用，**自动退回** v13 的房间内浏览式 `DirPicker`（不会报错、不会卡住）。
2. **`POST /open-in-app/open` 在本机是否 200、是否需要登录 cookie，只能实机确认**（`dsh-host-open-in-app/lib/index.js:1195-1202` 有 Host/Origin + cookie 围栏）。失败会自动退回「复制路径到剪贴板」。
3. 运行中的宿主仍是 **v14**：v15 的三项改动要**重载 DSH** 才生效（`GET /dsh-room/rooms` 里现有的字段是 v14 的）。
4. 本版**没有**在真机上跑过「弹系统文件夹界面 → 换目录 → 与会者写文件进新附件目录」这条端到端链路，只有合成自测 + 静态取证；§5.1/§5.2 两个待实测点就是为此留的。
5. 去重只作用于插件的自动接力 ping；**成员本来就会各领一条**（每人 1 行），并不会让「3 条排队消息」变成 0 行——若同一位与会者已有别的来源（人类面板直发、其它插件）投进来的消息，那些仍按 DSH 原语义排队。
