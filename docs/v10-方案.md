## 0. 症状与取证（未能锁定唯一触发）

- 现象：用户停在「会议室」面板里，几秒后被弹回普通会话视图（外壳把当前面板选中态清掉了）。
- 实时采样（无需鉴权，插件路由直连）：`GET /dsh-room/rooms` 每 1.2 s 采 8 次、又每 0.5 s 采 120 s —— `room-muk1sk4l`(你好) 稳定 `rc=0 / seq=24`，`main`(主会议室) 稳定 `rc=3 / seq=157`；renderer 进程全程 `up`；到 19387 的 TCP 连接集合恒定（仅 22:16:35 多过一个瞬时连接）⇒ **不是轮询抖动、不是渲染进程崩溃、不是网络重连**。
- 无 `--remote-debugging-port`（拿不到 CDP）、`%APPDATA%\@deepseek-ai\dsh-desktop` 无 Crashpad 目录、`~/.dsh` 近 2 h 只有常规写入（无插件重载 / 无 `cordis.yml` 重写）⇒ **真机拿不到确定性时序**。
- 静态定位：整份 asar 里只有两处写 `panelInfo.activePanelId`，都在 `dsh/node_modules/@deepseek-ai/dsh-client-ui-layout/lib/client.js`：
  - `actions.selectPanel: (d, panelId) => { d.panelInfo.activePanelId = panelId }`
  - `actions.retainMainPanels: (d, panelIds) => { if (d.panelInfo.activePanelId !== null && !panelIds.includes(d.panelInfo.activePanelId)) d.panelInfo.activePanelId = null }`
  - 触发点：`const retainMainPanels = () => { instance.actions.retainMainPanels(ctx.slots.entries("main").flatMap((entry) => entry.options.key === void 0 ? [] : [entry.options.key])) }` + `ctx.slots.subscribe("main", retainMainPanels); retainMainPanels();`
  ⇒ **`main` 槽登记表任何一次变化，都会把「此刻不在表里的当前选中 key」清成 null**。
- 官方插件实践（asar 内 `dsh/node_modules/@deepseek-ai/dsh-agent-preset/skills/cordis-plugin-development/references/practices.md` @+6812）：`ctx.slots.inject(ownerKey, () => ctx.slots.register(...))` 的登记会在**属主声明折叠时被 dispose、恢复时重装**。⇒ 我们的 `main` 登记存在「我们不知情的缺席窗口」，宿主那一句 `retainMainPanels()` 正好落在窗口里，就把用户弹回会话。这是目前最贴合症状的解释，但**没有被真机时序证实**（见 §5）。

## 1. 设计：客户端自愈（不动宿主）

### 1.1 粘性守卫

- `panelGuard = { wasOurs, lastGestureAt, lastSessionsAt, lastRescueAt, selfClearAt, giveUp, rescueTimes[], busy }`（`client.js:759`）。
- `watchPanelGestures(ctx)`（`client.js:774`）：`window.addEventListener('pointerdown'|'keydown', …, true)` 记 `lastGestureAt`；`ctx.sessions.list.subscribe(…)` 记 `lastSessionsAt`（该服务不存在时整个 try/catch 退化，只用手势信号）。
- `followActive(ctx)`（`client.js:790`）里的 `applyInfo`：
  - `ours = id === PANEL_ID || id.startsWith('dsh-meeting-room:result:')`；
  - ours ⇒ `wasOurs = true`（若已 `giveUp` 且 1.5 s 内有手势 ⇒ `guard-reset` 解除放弃）；
  - id 非空且非 ours ⇒ `wasOurs = false`（用户自己切去了别的全局面板，不干预）；
  - id 为空且 `wasOurs` ⇒ 算 `navigated = (now - selfClearAt < 1500) || (now - lastSessionsAt < 700) || (now - lastGestureAt < 1200)`：**是用户主动导航就尊重**；否则抢回。
- 抢回：6 s 窗口内超过 3 次 ⇒ `giveUp = true` 停手（避免和外壳对打 / 无限闪烁）；否则 `now - lastRescueAt > 400` 时限流一次。
- 用户点「返回会话」：`backToConversation()`（`:512`）先记 `panelGuard.selfClearAt = Date.now()` 再 `selectPanel(null)`，否则会被守卫立刻抢回。

### 1.2 抢回动作 = 先重挂 `main`，再设选中（v10.1 加固）

- 只把选中态设回来没用：宿主下一次 `retainMainPanels()` 还会清（见 §0）。所以抢回第一步是 `remountMain()`（`client.js:724`）：dispose 我们 `main` 的登记 → 立刻用同一 `key: PANEL_ID` 重新 `mount('main', { name:'main', key: PANEL_ID, label }, MainPane)` ⇒ key 回到登记表；随后才 `selectPanel(PANEL_ID)`。
- `panelGuard.busy`：抢回期间（重挂会同步引来宿主的清空回声）`applyInfo` 首行 `if (panelGuard.busy) return;`（`:795`）⇒ 回声不被计成新一轮「被清空」，不会几次回声就把 3 次机会烧光直接 `giveUp`。
- 侧边栏那一行（`sidebar.panellist`）不动：`applyRoomRows()` 的 signature 未变，真机观感上只是面板内容重回会议室。

### 1.3 诊断环（为「真机再复现」留证据）

- localStorage key `dsh-meeting-room.panel-diag`，JSON 数组 ≤60 条；kind ∈ `enter / leave / cleared / rescue / giveup / guard-reset / register / register-failed / inject-failed / unmount-main / remount-main`。
- 真机若再被弹走：控制台读这个 key 就能看出「谁清空的、守卫有没有抢、是不是已经放弃」。

## 5. 诚实边界

- **根因未被真机时序证实**：§0 的 `retainMainPanels` 路径是最贴合症状的机制解释（全 asar 只有它和 `selectPanel` 会写这个字段），但采样期没抓到清空瞬间。守卫是「外壳清空我们面板时自愈」的兜底；若真实触发另有路径（例如宿主把整个 slot 声明折叠、每次都吃掉登记），守卫会在 6 s 内 3 次后 `giveUp` 停手 —— 那时请读 `dsh-meeting-room.panel-diag` 定位，不要以为守卫万能。
- 探针用的是**假时钟 + 桩 ctx**：能证明「给定清空序列时守卫的决策与重挂动作」，不能证明真机 100% 不再复现；真机确认仍需用户肉眼观察。
- 没有 CDP / 没有真机自动化（浏览器侧 token 是签名负载，无法离屏复用 GUI 连接）⇒ **本版结论是「读源码 + 自测 + 独立探针 + 变异测试」核实的，不是重启后的真机复现**。
- 诊断环写在 localStorage：只存面板 id 与时序，不含会话内容；上限 60 条，满则丢最旧。
