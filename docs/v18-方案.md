# v18 方案 —— 真机 bug 修复：与会者的权限申请只弹在会话页

> 用户原话（m05967）：「与会者的权限申请依然要我到会话页面批准，就这件事你继续解决，开发原则：遵循最小代码改动原则，检查 bug 与核验功能，保证稳定性。」
>
> 一句话结论：**这不是 v17② 的「面板没渲染」，而是插件注册监听器太晚** —— DSH 把 `approval/request`
> 转发给浏览器（会话页那套审批弹窗）的那个「桥」注册得比本插件早，而且它**会阻塞等用户在会话页点按钮**，
> 排在它后面的监听器永远轮不到。v18 只做三件事：把监听器 `prepend` 到最前面、把 id 前缀写法归一、
> 加一条只读诊断让人一眼看出监听到底有没有被叫到。

本版**只改 1 个文件的行为**（`index.js`），客户端与配置项零改动，工具仍 13 个，端点仍是「只增一条只读诊断字段」。

## 1. 取证：为什么请求只去了会话页

### 1.1 先确认「不是没重载」

真机（`http://127.0.0.1:19387/dsh-room`，运行中的宿主）：

```
GET /dsh-room/staging                     → 200 {"root":"C:\\Users\\uyiop\\AppData\\Local\\Temp\\dsh-meeting-room", ...}
GET /dsh-room/rooms/room-munqtq0q/approvals → 200 {"approvals":[]}
GET /dsh-room/rooms/room-muo15ti5/state    → room 字段里已有 "approvals"（v17 新增）
```

`/rooms/:id/approvals` 与 `RoomSummary.approvals` 都是 v17 才有的东西，所以宿主加载的确实是 v17② 代码，
问题出在**注册时机**，不在「代码没生效」。

### 1.2 逐条排除

| 假设 | 结论 | 依据 |
| --- | --- | --- |
| 被 `dsh-scope` 的 agent scope 过滤挡掉 | **排除** | `dsh-scope/lib/index.js:327-338` `scopeTarget()`：`const tag = scopeOf(ctx); if (tag === void 0) return true;` —— 插件 ctx 没有 scope 标记 ⇒ 本来就会放行 |
| 会话 policy = `never`，请求在到达 answerer 前就变 reject | **排除** | `never` 时请求根本到不了监听器，用户也看不到会话页弹窗；而用户看到的是弹窗 |
| `ctx.on` 注册失败（走了 `warn` 分支） | **排除** | 宿主 ctx 有 `ctx.on`（v16③ 早就用它注册过 `systemPrompt`，同仓 `index.js:2268` 还在用 `ctx.on(..., { prepend: true })`） |
| 面板没渲染 `room.approvals` | **排除** | 客户端横幅 v17 就写好了（`client/client.js:1569-1581`），且诊断端点回的是空数组 ⇒ 请求压根没进过 `this.approvals` |

### 1.3 真身：浏览器转发桥「先注册 + 阻塞」

`C:\Users\uyiop\AppData\Local\npm-cache\_npx\1e7f6d9597241db0\node_modules\@deepseek-ai\dsh-api-remotes\lib\index.js`：

- 白名单（`:17-94`）里明确有 `{ event: "approval/request", mode: "waterfall" }`；
- `apply()` 用 `ctx.effect(() => ctx.typertGateway.registerRemoteEvents(...))`（`:101-103`）注册；
- waterfall 分支（`:115-125`）：

```js
ctx.on(event, function(request, next) {
  ...
  return forwardWaterfall(queue, event, request, {...}, next)
});
```

- `forwardWaterfall`（`:183-200`）把请求 push 进队列**交给浏览器**，只有浏览器回 `kind !== 'result'`
  或队列关闭时才 `next()`；否则它返回一个「等浏览器作答」的 promise —— **排它后面的监听器永远没机会被调用**。

会话页那套审批弹窗完全由这个转发驱动：`dsh-client-ui-approval/lib/client.js:282-284`
`ctx.remote.$on("approval/request", function(request, next) { answerApproval(ctx, this, request, next, ...) })`。
⇒ 只要请求进了浏览器，会话页就一定会弹窗；而我们要接管，就必须**坐在这个桥前面**。

### 1.4 cordis 的 `prepend` 与上游的注释

- `dsh-user-approval/lib/types/index.js:167-204`（同 `lib/index.js:179`）：`decide()` 先按会话 policy
  短路（`never → 'rejected'`），再
  `this.ctx.waterfall(scopeTarget(req.agent, req.agent), 'approval/request', req, () => Promise.resolve('unavailable'))`；
  该文件 `:171-175` 的注释明确写着：**`prepend: true` 注册的监听器会坐在先注册的监听器前面**。
- `@deepseek-ai/cordis/lib/index.js`（v4.0.2）：`register` 内 `const method = options.prepend ? "unshift" : "push"`（`:336`）；
  `on(type, listener, options)` 的 boolean 简写即 `{ prepend }`（`:368-372`）。

探针文件 `C:\Users\uyiop\dsh\dsh-meeting-room\.probe-approval-order.mjs`（临时，交付前已删），

## 2. 实现（插件侧只动 `index.js`，另加自测脚本一行）

### 2.1 监听器抢位（`index.js:1188-1196`）

```js
const approvalOptions = { global: true, prepend: true };
this.ctx.on('approval/request', (req, next) => this.handleApproval(req, next), approvalOptions);
this.approvalOptions = approvalOptions;
this.approvalsReady = true;
```

- `prepend: true` = 真正解决问题的那一半（cordis `unshift`）。
- `global: true` 是保险：本插件 ctx 没有 scope 标记，按 `dsh-scope` 的过滤本来也会放行，写上更明确。
- 实际用的 options 存进 `this.approvalOptions`，由诊断端点照实回报（不写死「应该是什么」）。

### 2.2 id 前缀漂移（`index.js:1202-1214`）

```js
const key = String(sessionId);
const bare = key.replace(/^session-/, '');
for (const room of this.rooms.values()) {
  for (const [id, member] of room.members) {
    if (id === key || String(id).replace(/^session-/, '') === bare) return { room, member };
  }
}
```

房间成员表里存的是 `session-<uuid>` 形态，而审批请求的 `req.agent.id` 在别的装配下可能是裸 `<uuid>`
（或反之）。只要两边的「裸 id」相等就认得出 —— 否则会出现「明明是本房间成员却当成外人放回原链」的静默失效。

### 2.3 只读诊断环（`index.js:1154` / `:1242-1245` / `:1252`）

```js
handleApproval(req, next) {
  const sessionId = req?.agent?.id ? String(req.agent.id) : '';
  const toolName = String(req?.toolName ?? '') || '未知操作';
  const hit = this.roomOfMember(sessionId);
  this.recordApproval({ sessionId, toolName, callId: req?.callId ?? null, roomId: hit?.room?.id ?? null, matched: !!hit });
  if (!hit) return next();
  ...
```

**先记账、再判成员**：这样「监听到底有没有被叫到」和「是不是被成员判定挡回去」两件事可以分开看，
环形只留最近 20 条（`recordApproval`），不影响任何行为。

### 2.4 诊断端点（`index.js:2949`）

`GET /dsh-room/staging` 的响应里多一段：

```js
approvals: { ready: !!host.approvalsReady, options: host.approvalOptions ?? null, pending: host.pendingApprovals(), seen: host.approvalsSeen.slice(-20) }
```

只读，不改任何状态。真机复验时一条 curl 就能判断：
`ready/options` 证明「新代码注册成功且带了 prepend」，`seen` 证明「请求确实被听过、`matched` 是不是 true」，
`pending` 证明「有没有挂上面板等着点」。

### 2.5 客户端 / 配置项 / 工具面：零改动

- 客户端横幅（`client/client.js:1569-1581`）v17 已写好：`room.approvals` 非空就渲染「允许 / 拒绝」，
  与房间是开着还是散会无关，所以 v18 不需要动客户端。
- 工具仍 13 个；配置项零新增；HTTP 端点只多了 `staging` 响应里的一个字段（端点数量不变）。

## 4. 诚实边界

1. **必须重载 DSH 才生效。** 插件跑在宿主里，v18 的三处改动都在宿主侧；不重载依旧是旧行为。
2. **只有在宿主真的产生 `kind:'ask'` 请求时才会弹横幅。** 默认装配里 ask 主要来自
   `dsh-hooks-claude-code` 那条 pre-execute 判定，或模型在工具参数里主动申请提权（`sandbox_permissions`）；
   没人申请权限时，会议室面板一切照旧（不是「坏了」）。
3. **会话 policy = `never` 时永远不弹。** 那种配置下请求在到达任何 answerer 之前就确定性变成 reject，
   监听器根本看不到（这是 DSH 的既有语义，不是本插件的 bug）。
4. **授权是一次性的。** DSH 只提供 `'allowed-once'`，没有「记住这个工具以后都允许」；每次都要点。
5. **120 秒不点就退回原链。** 退回后与会者会在**它的会话页**等审批（这是刻意保留的兜底，不是漏改）。
6. **`prepend` 抢的是「浏览器桥前面」，不是「用户的策略前面」。** 我们只拦本房间成员，非成员一律
   `next()`，不改变 DSH 原有审批行为（探针 `[5]` 已验证）。
7. **诊断端点只读。** `GET /dsh-room/staging` 的 `approvals` 段不写任何状态；不想要也可以忽略。
8. **`prepend` 依赖 cordis 的事件语义。** 本仓 `index.js:2268` 早就用同样的 `{ prepend: true }`
