## 1 取证

### 1.1 ① 批准重开为什么「静默」（`index.js` 旧 `case 'reopen'`）

- 旧代码的 `by:'user'` 分支只做五件事：`status='open'`、`closedAt=null`、`reopenRequest=null`、`saveRoom()`、`if (wasClosed) appendSystem('会议已重开')`。
  ⇒ **零投递**：没有任何 `deliver`、没有 `activate`，与会者根本没被叫醒，所以真机症状就是「批准了，但房间没人说话」。
- 同文件另外两条重开路径也不投递（同一根因）：
  - `by:'member'`：只写 `room.reopenRequest = {sessionId, by, at, reason}` + `appendSystem('X 请求重开…')`；
  - 目标级「再议」`POST /rooms/:id/goals/:gid/reopen`：`goal.status='active'` + 旧结果标 `superseded` + `appendSystem('发起再议：…')`。
- 可直接照抄的投递模板是 v16③(b) 的驳回：`deliver({ text, kind:'reject', authorLabel:'审核意见', targets:[...room.members.keys()], mode:'full', latestSeq: room.seq })`，外层 `try/catch` + `host.warn`。
- `deliver` 是唯一投递漏斗（`index.js` `async deliver({text, kind, authorLabel, targets, mode, senderSessionId, latestSeq, count, noticeStyle})`）：`mode:'full'` 走正文直达，`mode:'notice'` 走可合并的「有新消息」ping；内部循环 `this.host.activate(member.sessionId)` + `relayWithEffort(...)`，**投递本身就等于把讨论推起来**。

### 1.2 ② DSH 到底怎么建模「权限」（只读调研，实现树 = 插件包树）

> ⚠️ 路径更正：`C:\Software\DeepSeek Harness\resources\app.asar\dsh\` **不存在**（asar 未解包）。
> 真实实现是插件包树，稳定入口 `C:\Users\uyiop\.dsh\profiles\node_modules\@deepseek-ai\`（junction 指向 npm-cache 下的 `node_modules\@deepseek-ai`）。

- **没有** `permissionMode` / `bypassPermissions` / `acceptEdits`（全库 0 命中）。权限是**两个独立旋钮**，都以会话日志事件存储（log-only、可重放、不进模型 transcript，最后一条覆盖）：
  - `export type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'`（`dsh-sandbox/lib/types/index.d.ts:19`），事件 `'sandbox/mode'`（`dsh-sandbox-policy/lib/types/session-mode.d.ts:31`）；
  - `export type ApprovalPolicy = 'ask' | 'never'`（`dsh-user-approval/lib/types/index.d.ts:46`），事件 `'approval/policy'`（同文件 `:26`）。
  - 写入 API：`setSandboxMode(session, mode)`、`setApprovalPolicy(session, policy)`、实时 `setPolicy(agent, policy)`、预设层 `permissionPresets.set(session, name)`（默认 `workspace-write` = workspace-write + ask；`danger-full-access` = danger-full-access + never）。
  - `SessionHeader`（`dsh-session/lib/types/types.d.ts:58-94`）**没有任何权限字段**。
- **审批请求怎么产生**：`dsh-tools/lib/index.js:3330` `const outcome = await approval.request({ agent, toolName, callId, reason?, signal })`；`ask` 来自 `'tools/pre-execute'` waterfall 的 `PreToolDecision = {kind:'allow'} | {kind:'deny', reason} | {kind:'ask', reason?}`。另一条是沙箱提权 `approveEscalation`。
- **怎么应答（可行性的核心）**：`'approval/request'(this: Scoped<Agent>, req: ApprovalRequestEvent, next: () => Promise<ApprovalOutcome>): Promise<ApprovalOutcome>`（waterfall，`dsh-user-approval/lib/types/types.d.ts:76`）；
  `ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'`（`:26`）；`req = { agent, toolName, callId?, reason?, signal? }`。
  **真实插件就是这么答的**：`dsh-acp/lib/index.js:1115` `ctx.on("approval/request", (request, next) => { … return outcome.optionId === "allow-once" ? "allowed-once" : "rejected"; })`；浏览器侧白名单通道 `dsh-client-ui-approval/lib/client.js:282` `ctx.remote.$on("approval/request", …)`。
- **三条硬约束**：
  1. 唯一授权值是 `'allowed-once'`，**没有持久授权**（`dsh-user-approval/lib/types/index.d.ts:123`）；
  2. 必须在 open turn 内，否则 `approval.request() outside an open turn: the approval/asked + approval/decided audit pair must be turn-enclosed`（`dsh-user-approval/lib/index.js:133`）；
  3. `policy='never'` 时 ask 在到达 answerer 之前就确定性变 reject（`index.d.ts:42-44`），**监听器根本看不到**。
- **无 per-tool allowlist**（`allowedTools` 在审批语境 0 命中）。等效做法就是「监听器恒返 `'allowed-once'`」或「直接把会话设成 danger-full-access / never」。
- `host.agentOf` / `host.warn` / `HostApi` 在 DSH 本体 **0 命中** —— 那些是会议室插件自己的包装层名字，不是 DSH API。真实入口：`ctx.get('approval')`（`dsh-tools/lib/index.js:3315`，取不到即 fail-closed deny）、`ctx.approval`、`ctx.permissionPresets`、`ctx.sandboxPolicy`、`ctx.agents`；未加 scope 的监听器**全局**收到所有 agent 的请求（`dsh-scope/lib/types/index.d.ts:86-92`）⇒ 我们必须自己按 sessionId 过滤。
- **结论：Host 侧插件做「在会议室里批准 / 拒绝与会者权限」完全可行**；唯一实际障碍是**时序**——只在「有人正在问」时才存在请求（工具须返回 `kind:'ask'`；默认组装里只有 `dsh-hooks-claude-code` 产出，与会者也可主动用 `sandbox_permissions` 提权），且该会话 policy 必须为 `ask`、必须处于 open turn。

## 2 实现

### 2.1 ① 批准重开 ⇒ 立刻投递全体（`index.js:3238-3286`）

`by:'user'` 分支改成（`index.js:3252-3285`）：

```js
const wasClosed = room.room.status === 'closed';
const pending = room.room.reopenRequest ?? null;   // 先留住申请人 / 理由，再清
room.room.status = 'open';
room.room.closedAt = null;
room.room.reopenRequest = null;
await room.saveRoom();
if (wasClosed) await room.appendSystem('会议已重开');
if (wasClosed || pending) {
  const activeGoal = room.goals.find((goal) => goal.id === room.room.activeGoalId) ?? null;
  const why = reason || String(pending?.reason ?? '').trim();
  const reopenText = [
    '会议已重开，请立即接着讨论。',
    activeGoal ? `当前会议目标：${activeGoal.text}` : '当前没有进行中的会议目标，请按会议记录里最后的议题继续。',
    why ? `重开原因（${pending?.by || '与会者'}）：${why}` : null,
    '先用 room_read 看完整记录（尤其是散会前后的结论与待办），再围绕目标继续；有结论用 room_goal_report 反馈「达成 / 有分歧」。',
  ].filter(Boolean).join('\n');
  try {
    await room.deliver({ text: reopenText, kind: 'reopen', authorLabel: '主持人',
      targets: [...room.members.keys()], mode: 'full', latestSeq: room.seq });
  } catch (error) {
    host.warn(`重开后投递失败：${error?.message ?? error}`);
  }
}
```

要点：
- **`mode:'full'`**：正文直达，不走会被 v15② 原地替换去重的 ping；`deliver` 内部对每位与会者 `activate` + 接力，等于替用户把讨论推起来。
- 触发条件是 `wasClosed || pending`：**已有 pending 申请**时即使用户批准的是一次「本来就开着」的房间，也照样推一把（不会漏投）。
- 投递失败**不影响重开本身**（状态已经落盘），只在宿主日志里留一行 `重开后投递失败：…`。

### 2.2 ② 会议室里的实时审批（`index.js`）

新增常量与状态：

- `const APPROVAL_WAIT_MS = 120000;`（`index.js:1129`，`class MeetingHost` 之前）；
- 构造函数：`this.approvals = new Map();`（`index.js:1149`，`callId -> 待批项`）、`this.approvalsReady = false;`（`:1150`）。

新增方法（`index.js:1170-1266`，`warn()/info()` 之后）：

| 方法 | 行 | 作用 |
|---|---|---|
| `installApprovals()` | `:1176` | `this.ctx.on('approval/request', (req, next) => this.handleApproval(req, next))`；拿不到 `ctx.on` 就 `warn('宿主没有 ctx.on，与会者的权限请求只能在它自己的会话里批准')` 并返回 `false`（**不抛、不影响其它功能**） |
| `roomOfMember(sessionId)` | `:1192` | 遍历 `this.rooms` 找 `room.members.get(sessionId)` ⇒ `{room, member}` / `null` |
| `pendingApprovals(roomId)` | `:1201` | 回可见列表 `{ callId, sessionId, roomId, label, toolName, reason, at }`（按 `at` 排序） |
| `decideApproval(callId, allow, roomId)` | `:1218` | 落一次决策：找不到 ⇒ `{ ok:false, status:409, error:'这个权限请求已经失效（可能已超时，交回它自己的会话审批了）' }`；房间不符 ⇒ 404 |
| `handleApproval(req, next)` | `:1227` | 非成员/非本房间 ⇒ `return next()`；否则登记 `this.approvals.set(callId, …)` 并返回一个 Promise：`allow ⇒ 'allowed-once'`、`deny ⇒ 'rejected'`、`req.signal` abort ⇒ `'cancelled'`、120 s 超时 ⇒ `resolve(next())` |

```js
handleApproval(req, next) {
  const sessionId = req?.agent?.id;
  const hit = this.roomOfMember(sessionId);
  if (!hit) return next();                                  // 不是与会者：原样交回审批链
  const callId = req.callId || `${sessionId}:${req.toolName}:${Date.now()}`;
  return new Promise((resolve) => {
    const ask = { callId, sessionId, roomId: hit.room.id, label: hit.member.label,
      toolName: req.toolName, reason: req.reason ?? null, at: Date.now(), finisher: null, timer: null };
    const finish = (decision) => {
      if (ask.finisher) return;                              // 只 settle 一次
      ask.finisher = decision;
      clearTimeout(ask.timer); ask.timer = null;
      this.approvals.delete(callId);
      resolve(decision === 'allow' ? 'allowed-once'
        : decision === 'deny' ? 'rejected'
        : decision === 'cancel' ? 'cancelled' : next());
    };
    ask.finisher = null;
    ask.timer = setTimeout(() => finish('timeout'), APPROVAL_WAIT_MS);
    ask.timer?.unref?.();                                    // 不拖住进程退出
    req.signal?.addEventListener?.('abort', () => finish('cancel'), { once: true });
    this.approvals.set(callId, ask);
    this.info(`与会者「${ask.label}」请求使用 ${ask.toolName}，已挂到会议室面板等批准`);
  });
}
```

下发给面板与端点：

- `Room.summary()` 末尾加 `approvals: this.host.pendingApprovals(this.room.id),`（`index.js:758`）⇒ 随 `GET /rooms/:id/state` 的 `room` 每次轮询下发，面板据此弹横幅（不必再开第二条轮询）。
- 房间级端点 `case 'approvals':`（`index.js:3226-3237`，插在 `case 'reopen'` 之前）：
  - `GET` ⇒ `{ approvals: [...] }`；
  - `POST` ⇒ body `{ callId, decision:'allow'|'deny' }`，非法 decision ⇒ **400**「decision 只能是 allow / deny」；`decideApproval` 失败按 `out.status ?? 409` 抛；成功 ⇒ `{ ...out, room: room.summary() }`；
  - 其它方法 ⇒ **405**「只支持 GET / POST」；
  - **`callId` 走 body**：`index.js:2769` 的路由是 `url.pathname.slice(API.length).split('/').filter(Boolean)`，**不做 URL 解码**，塞进路径不安全也不可靠。
- 挂载点：`apply()` 里 `host.staging = new MeetingStaging(host);` 之后 `host.installApprovals();`（`index.js:2832`）。

### 3.3 自查中抓到并修掉的两个真问题（写出来是为了别重犯）

1. **端点方法分流错了会「静默挂死」整轮自测**：第一版 `case 'approvals'` 用 `if (tail.length === 1)` 判 GET，而 POST 的 `callId` 走 body 时 `tail` 长度也是 1 ⇒ POST 被当成 GET 回 `{"error":"只支持 GET"}`（断言失败），紧接着测试 `await` 那个**永远不 settle** 的审批 Promise ⇒ 整轮自测无输出挂死 >10 分钟。
   修法：**按 `method` 分流**（`GET` 列待批、其它非 POST 405），而不是按路径长度。
2. **自测要能报告实现漏 settle，而不是挂死**：新增 `const settleWithin = async (promise, ms = 3000) => Promise.race([promise, new Promise((resolve) => { const timer = setTimeout(() => resolve('__timeout__'), ms); timer.unref?.(); })])`，包住所有审批 Promise ⇒ 实现有 bug 时是 FAIL，不是 hang。

## 4 诚实边界

1. **② 只在「宿主真的在问」时才有横幅可弹。** 默认组装里只有 `dsh-hooks-claude-code` 会产生 `kind:'ask'`，与会者也可以主动用 `sandbox_permissions` 提权；两者都不发生时压根没有待批请求，会议室面板一切照旧（不会有空横幅）。此外该会话的 `policy` 必须是 `ask`——`never` 时 ask 在到达我们的监听器之前就确定性变 reject，我们看不到。
2. **答「允许」只放行这一次**（`'allowed-once'`）。DSH 没有持久授权、也没有 per-tool allowlist，所以会议室里**没有**「以后都允许」这种按钮；想少点弹窗只能把该会话设成 `danger-full-access`（那是 DSH 自己的权限界面/预设的活，不在本次改动范围）。
3. **120 秒不点就等于没接住**：请求会 `next()` 交回 DSH 原审批链（去它自己的会话里答）；此时面板上那条横幅消失，再点会 409。这是刻意选的**安全默认**（不替用户永久挂起会话），但也意味着长会议里若你离开 2 分钟，权限请求会退回原渠道。
4. **待批请求只活在内存**：宿主重载 / 崩溃即清空（那条 `ask` 也随 turn 结束而作废），本次没有落盘。
5. **真机行为未复验**：写下这段时跑着的宿主仍是**旧版插件**（v16 时 `GET /dsh-room/staging` → 404），①② 需要用户**重载/重启 DSH** 后才在真机生效；③ 是纯客户端，刷新页面即可见。自测用的是 stub `agents` / `llm`，不构成端到端证据。
6. **③ 的观感需目视**：数字条在输入框下方的间距、长提示删掉后的留白、审批横幅在窄栏里换行——agent 看不到屏幕，需重载后由用户确认。
7. **① 的投递不可回滚**：一旦批准就投一条全文给全体并接力；若你其实只是想改个状态、不想真的把大家叫起来，目前没有「只重开不投递」的开关（如需要请说，属于可加的最小选项）。
