# v12 方案：修掉「记录员报错 + 不整理文件」，并加上「任务完成」指令与文件管理

> 用户原文（User said, m00269，摘意）：「两个 bug：我在**结束会议**与**标记达成目标**以后会弹出红框报错，记录员也没有开始记录，也没有整理文件」；并附两条要求：
> ①**加入类似普通会话里「任务」的机制**：讨论得出结果后，直接向系统发送「完成任务」的指令，由记录员再进行记录；
> ②**策划会议里加入文件管理**：(a) 决定会议文件是**全部保存**还是**只保存记录员的记录**；(b) 一切会议产生的文件**默认放在一个文件夹里**（可选**新增**或**选择已有**文件夹），不要乱放。
> 用户补充（User said, m00280）：「**请注意最小变动原则，且要核验功能完整性与稳定性**」。
> 用户定案（后续答复）：任务指令**由与会者 AI 调用工具发出**；记录员**指令到达即自动生成草稿**（仍由用户审核发布）；保存模式**只管「非记录员文件」要不要落盘**；目录形态是**房间文件夹下固定「记录/」「附件/」两个子目录**；附件**先照旧保存，散会/审核后自动清理**；入口复用房间已有的「会议文件目录」字段，**不另加全局默认根目录**。

## 0. 症状与取证（先证明「不是数据丢了，是前端提前放弃并误报」）

两张真机截图（`signal timed out` 红框）里 composer 文案已是 v11（「不设跳数上限」）⇒ 真机跑的是 v11 代码。只读取证：

- `GET /dsh-room/rooms/room-munqtq0q/goals`：目标 `1e831740…「就湿纸巾一词发表文章」` 状态**已是 `done`**，`result.status='draft'`、23KB 草稿已在，`doneAt:1790751914184`。
- `result.at`（1790751967035）− `doneAt` = **52 851 ms ≈ 53 秒**。客户端弹红框的那一刻，宿主记录员**还在一动不动地跑 LLM**；等它跑完（≈53 s），草稿与 `记录/结果/<gid>.md` 都写成了。

⇒ **真正的 bug 是超时口径不一致**：客户端所有 JSON 请求挂 8 秒 `AbortSignal.timeout`，而「标记达成 / 散会」在宿主里是 `await generateResultDraft(...)`（一轮记录员 ≈50 s）。客户端 8 秒先放弃、弹 `signal timed out`（DOMException.message 直接透传），用户看到的现象就变成「报错 + 记录员没开始记录」。**没有任何数据丢失。**

补充取证：`ctx.get('llm').stream(options)` 的 `GenerateOptions` 只有 `signal?: AbortSignal`，DSH 层无默认超时；宿主 webserver 也没有请求超时 ⇒ **宿主必须自己加看门狗**，不能指望 DSH 兜底。

## 1. 修复①：超时口径对齐 + 宿主看门狗（改前 / 改后）

### 1.1 客户端（`client/client.js`）

```js
// 改前（v11，:214-231）：所有请求一个 8 秒超时
opts.signal = AbortSignal.timeout(8000);

// 改后（v12，:214-245）
const DEFAULT_TIMEOUT_MS = 8000;
const RECORDER_TIMEOUT_MS = 300000;           // 触发记录员的接口：300s
async function json(path, init, timeoutMs) { /* … limit = timeoutMs ?? 8000 … */ }
const postJsonLong = (path, body) => json(path, { method:'POST', body: JSON.stringify(body||{}) }, RECORDER_TIMEOUT_MS);
```

超时抛出的文案也换成人话：`等待超过 N 秒没有回应（记录员可能还在写，稍后刷新看看）`（只有长超时才带括号说明）。改走 `postJsonLong` 的只有两处 ——「标记达成」（`client/client.js:1640`）与「散会」（`client/client.js:1880`），并且都读回 `reason` 再提示（`完成但未生成草稿：…` / `已散会；记录员未能整理结果：…`）。**其余接口仍是 8 秒。**

### 1.2 宿主（`index.js`，看门狗）

```js
const RECORDER_TIMEOUT_MS = 240000;   // :51
const watchdogMs = Number(this.host?.config?.recorderTimeoutMs) > 0
  ? Number(this.host.config.recorderTimeoutMs) : RECORDER_TIMEOUT_MS;   // :887 附近
const controller = new AbortController(); if (controller) options.signal = controller.signal;
const armWatchdog = () => { clearTimeout(timer); timer = setTimeout(() => { overTime = true; controller?.abort(); }, watchdogMs); timer.unref?.(); };
```

- **惰性看门狗**：每收到一个 chunk 就重新计时 ⇒ 总时长无上限，只有「卡住 `watchdogMs` 没有任何返回」才放弃。**不用总时限**，否则正常的慢生成会被误杀。
- 放弃这轮时抛中文 503：`内置记录员这轮超过 240 秒没有任何返回（已放弃）：可以手动填写《会议结果》`，客户端因此拿到的是**真原因**而不是 `signal timed out`。
- 三个实现细节（都是踩出来的，改动最小但缺一不可）：
  1. 看门狗要**真的断流**：只置 `overTime` 拦不住挂在 `stream.next()` 上的等待 —— 自测里卡死流 5 秒后自己吐完，被当成成功返回 **200 + 半截草稿**。
  2. 所以循环不再用 `for await`，改成自己拉取，把「等下一个 chunk」和「abort」**赛跑**（哨兵 `ABORTED`，`index.js:53`）。
  3. 收尾时**故意不 `await iterator.return()`**：生成器若卡在自己内部的等待里，`return()` 也得排到那次 `next()` 之后才兑现（实测能拖满 5 秒），那样看门狗就白响了。改为 `Promise.resolve(iterator.return?.()).catch(()=>{})`。
- 失败原因**必须留在会议记录里**：新增 `noteRecorderFailure(reason, goal)`（`index.js:975`）→ `appendSystem('记录员没能整理出《会议结果》（目标：…）：…')`。只在面板弹一次红框，用户事后什么都看不到 —— 截图那个红框就是这么来的。
- `callRecorderModel` 里读时限用的是 `this.host.config.recorderTimeoutMs`（`Room` 本身没有 `config`；早先误写成 `this.config?.recorderTimeoutMs` ⇒ 恒回落 240s，自测里表现为「卡死用例拖满 5 秒还返回 200」）。
- 时限可配但**不给用户加开关**：`Config` 新增 `recorderTimeoutMs`（`index.js:79`，默认 240000，描述写明「自测会调小，用户不用改」），只是为了让自测不必真等 4 分钟。

## 2. 修复②：`room_task_done` —— 与会者 AI 发出的「任务完成」指令

已核实 DSH 的三种「任务」实体都不可用：`ctx.goals` 是**会话目标**（语义不符、且 `complete` 直接生效无人审核）、`todo_write` 无 service（外部调用报 `todo_write requires an owning agent session`）、`ctx.agentTeams` 要求 Team live member。⇒ 用插件自己的工具实现，形态跟 v3 起的 `room_goal_report` / `room_result_write` 一致。

新增第 13 个 Agent 工具（`index.js:3196`，插在 `room_result_write` 与 `room_request_reopen` 之间）：

- 参数：`roomId?`（缺省默认房间）、`note?`（给记录员的补充要求）。
- description 明确划界：**只在讨论真正得出结果、可以收尾时调**；只是汇报进展/有分歧请用 `room_goal_report`。
- 拒绝分支：非与会者 → `你还不在这个会议室里（先 room_join），不能宣告任务完成。`；没有进行中的目标 → `当前没有进行中的会议目标，不用宣告完成。`；已发布/已有草稿 → 各自的中文提示，不重复生成。
- 成功路径：`goal.status='done'` + `doneAt` + `history.push({action:'complete', by:label, note, via:'room_task_done'})` → `saveGoals()` → 写一条与会者消息 `任务已完成：<目标>（<label> / room_task_done），请<记录员>整理会议结果` → `await generateResultDraft(goal, note)`（**指令到达即自动出草稿**，仍由用户审核发布）→ 中文回执「已宣告任务完成（目标：…），记录员已提交《…》草稿，等用户审核发布。」
- 附带修一个陈旧状态 bug：`pickActiveGoal(exceptId)`（`index.js:736`）。原来目标达成后 `activeGoalId` 一直指着刚 done 的那个（要等重启 `load()` 才纠正），新目标 / `room_task_done` 都拿不到进行中的目标。现在 `action==='complete'`（`index.js:2585`）与 `room_task_done` 收尾后都把 `activeGoalId` 交给下一个未完成目标，没有就置空。
- 工具数 **12 → 13**：自测同步 `TOOL_NAMES` 与 `host.tools.length === 13`（`selftest/run.mjs:545`、`:551`、`:561`）。

## 3. 修复③：文件管理（保存方式 + 「记录/」「附件/」布局）

### 3.1 布局与迁移

```
<房间目录>/
  记录/                  ← 记录员的记录（resultsDir = 记录/结果）
    结果/<goalId>.md     ← 《会议结果》草稿/定稿
    .v12-migrated        ← 一次性迁移标记
  附件/                  ← 参会人上传等其它会议文件
```

- 常量：`RECORDS_DIRNAME='记录'` / `ATTACHMENTS_DIRNAME='附件'` / `RESULTS_DIRNAME='结果'`（`index.js:41-43`）；`setDir` 里 `recordsDir/resultsDir/attachmentsDir`（`index.js:391-392`），原 `filesDir` 属性整个删除（全仓 grep 无命中）。
- `migrateFileLayout()`（`index.js:411`，在 `load()` 的 `ensureDirs()` 之后调用）：旧 `files/`→`附件/`、旧 `results/`→`记录/结果`。**标记只用来跳过「没有旧布局」的常规启动** —— 若旧目录后来又出现（用户把 v11 的目录拷回来 / 上次搬到一半失败），仍会再搬一次。整段 try/catch 只 warn，不让整理拖死加载。
- 由此修掉一个真 bug：`moveDir` 原来无条件 `rename(from,to)`，`to` 已存在时 rename 会把 `from` 整个塞成 `to` 的子目录（实测 `dir/files` → `记录/结果/files`）。新增 `mergeDirInto(from,to)`（`index.js:269`）+ `if (await exists(to)) return mergeDirInto(from,to)`。

### 3.2 保存方式（`saveMode`，房间级，缺省 `all`）

- `saveMode ∈ {all, recorder}`（`SAVE_MODES` / `SAVE_MODE_LABEL`，`index.js:45-46`），`PATCH /rooms/:id {saveMode}` 落 `room.json` 白名单（缺了就会被重启吃掉，已补），非法值 400；变更时写系统行。**只管非记录员文件**，`记录/` 永远保留。
- `cleanupAttachments()`（`index.js:438`）：只有 `recorder` 模式才清 `附件/` 内文件（外加旧版遗留的「决议.md」），返回删除个数；单个失败只 warn。
- 触发点两处：**散会**（`index.js:2472`）与**《会议结果》发布**（`index.js:2720`）；`removed>0` 时写系统行说明删了几个。`DELETE /rooms/:id?purge=1` 仍是整体删。
- 散会响应新增 `saveMode` 字段（`index.js` 的 `case 'close'|'adjourn'`），客户端/自测不必再单独 GET 房间。

### 3.3 面板（客户端 `DrawerFiles`）

`PlannerDrawer` body 顺序：`DrawerGoals → DrawerMembers → DrawerRecorder → DrawerDelivery → **DrawerFiles** → DrawerControl`（`client/client.js:1598`，组件定义 `:1802-1860`）：

- 「保存方式」两个按钮（`patchJson('/rooms/:id', {saveMode})`），下方一行提示随模式切换（recorder = 散会/发布后会清附件；all = 不会自动清）。
- 「存放位置」：显示 `会议文件目录：…` + 「在文件夹中打开」（复用 `revealDir`）+ 「新建子文件夹」（拼出 `<父目录>\<名字>` 后 `PATCH {dir}`）+ 「选择已有文件夹」（复用已有 `DirPicker`）。
- 宿主 `PATCH /rooms/:id {dir|category}` 本来就会 `mkdir` 并整体搬目录，**所以没有新增任何端点**。房间摘要新增 `saveMode` / `recordsDir` / `resultsDir` / `attachmentsDir` 四个字段供面板直接显示。
